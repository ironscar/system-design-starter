# New Solution (after peer review)

## Functional Requirements

- Given a long URL with parameters etc, generate a distinct short URL for it
- The short URL generated must always go to this long URL only

## Non-functional Requirements

- The one-time process of generating the initial short URL can take more time if required
- The process of getting the long URL back from the short URL must be fast
- The short URLs should be as short as possible
- It would be good to have the same long URL always map to the same short URL to reduce duplication in database
- We may require a way to decommission URLs whose corresponding short URLs maybe reused for new long URLs
- System needs to be highly available and low latency regardless of geographical location

## Scale Considerations

- There are about 3.5M domains and then each domain will further have more path extensions with fewer encodings
  - assume 5 segments, 5 types of values for each segment on average => 5^5 combinations * 3.5M domains = 10B URLs
  - then we have path variables and parameters, assume 5 combinations per URL on average => 50B URLs (we expect those without such combinations to compensate for those with open-ended param values)
- There may be upto 20M new short URLs generated per day => 232 requests per second

## Architecture Steps

1. Start with the simplest way and find out problems
2. Then start building up to fix each of the problems by priority

## Solution Design

### General Details

- Encode the short URL into `[a-zA-Z0-9]` => 62 characters
  - these are regular URL characters
  - we could use `-` and `/` but these are often used for separators so prefer to not use them for encoding

### Architecture Decision Records

1. `ADR1`: Do we use fixed-length encoding or variable-length encoding?
  - `DECISIONS`
    - `OPT 1` has fewer combinations to use so we can do better
    - `OPT 2` has most combinations but a one-character-URL would look weird so we skip this for user experience issues
    - `OPT 3` has a good balance of more number of combinations available and looking like a viable short URL `[SELECTED]`
  1. `OPT 1`: Fixed length encoding
    - PROs
      - short URL looks fine
      - doesn't have an upper limit to what can be supported
    - CONs
      - fewer number of combinations than would be possible with using variable length encodings as `aa` and `a` can coexist in the latter
  2. `OPT 2`: Variable length encoding starting at 1
    - PROs
      - most number of combinations available
    - CONs
      - a short URL with just 1 character looks weird
  3. `OPT 3`: Variable length encoding starting at `k (say k = 5)` and can grow as per usage
    - PROs
      - more combinations available than fixed length encoding
      - short URL looks fine 
      - doesn't have an upper limit to what can be supported
2. `ADR2`: What are the main ways you can store the data?
  - `DECISIONS`
    - `OPT 1` won't work because it has the probabaility of hash collisions which violates one of our functional requirements
      - Cuckoo hashing and rehashing won't be considered here as both involve rehashing existing entries to new ones which violates one of our functional requirements
      - Thus, `separate chaining (OPT 1.1)` and `open addressing (OPT 1.2)` will be considered next
  1. `OPT 1`: Every URL has a mapping generated by an encoding function from the URL directly
    - PROs
      - Can run a single function directly on input to figure out the encoding
    - CONs
      - To shorten the URL, we must represent more information with lesser characters which has a limit in scale and will also lead to hash collisions
  2. `OPT 1.1`: Every URL has a mapping generated by an encoding function but also addresses hash collisions via separate chaining
    - Details
      - Storing 50B URLs with Base 62 encoding => `5 characters` (62^5 = 56B)
  3. `OPT 1.2`: Every URL has a mapping generated by an encoding function but also addresses hash collisions via open addressing

## Findings

### Hash Collision Resolution Strategies

1. `Separate chaining (open hashing)`: each hash key is associated to a list of colliding entries
   - the index of the list effectively becomes part of the hash key but performance degrades with collision sizes
   - good write performance but read performance maybe affected
2. `Open addressing (closed hashing)`: each hash key is associated to exactly one entry but if there is a colliding entry, then probe for a new available key
   - `linear probing` looks for the `index+1`, `index+2`... keys and assigns the first available one
   - `quadratic probing` looks for the `index + 1^2`, `index + 2^2`... keys and assigns the first available one
   - `double hashing` uses a second hash function to calculate step size for probing
   - good read performance but write performance can suffer
3. `Cuckoo hashing`: uses multiple hash functions and kicks out the existing element to an alternative location to make space
   - existing element may end up on a collision while getting reassigned which would become part of the write
   - good read performance but write performance can suffer
4. `Rehashing` just creates a larger hashing table when the current table size doesn't suffice thereby requiring a full lift-and-shift
